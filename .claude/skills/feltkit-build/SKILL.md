# FeltKit: build an application

FeltKit runs one application on one FeltDB instance per environment, exposed through AppPort. You change the
application by editing TypeScript in `feltkit/`; the dev server reloads it without reopening state.

**This skill is guidance, not authority.** Roles in `feltkit({ roles })` decide what any caller may do, on every
interface. Nothing here grants a permission.

## Project layout

```
feltkit/app.ts            the application: feltkit({ name, roles, dev, services })
feltkit/<module>.ts       functions; each export is "<module>:<export>" (tasks.ts list → "tasks:list")
feltkit/_generated/api.ts generated by `feltkit dev` / `feltkit codegen`; never edit
src/                      the frontend (Vite + React)
tests/*.test.ts           run by `feltkit test`
.feltkit/<env>/           local state and the admin token; never commit, never print the token
```

## Workflow: add a feature

1. Read `feltkit/app.ts` and the module you will change. Run `npx feltkit inspect --json` for the live picture.
2. Declare data with `app.collection(name, shape)`; names starting with `_feltkit`, `_flow`, `_feltdb`, `_appport`, and AppPort Services' collections are reserved.
3. Write functions with `app.query` / `app.mutation`. Give each an `access` permission (or `"public"` / `"authenticated"`).
4. To expose a function to AppPort clients and agents, add `capability: { name: "<noun>.<verb>" }` **and** a `returns` schema.
5. Grant the permission to roles in `feltkit({ roles })`. Use `npx feltkit dev`; check the dashboard's Capabilities screen.
6. Add or update a test with `createTestApp`; run `npx feltkit test`. Then `npx feltkit build`.

```ts
// feltkit/app.ts
import { feltkit, s } from "@feltdb/feltkit";
export const app = feltkit({
  name: "tasks",
  roles: { member: ["tasks.*"], viewer: ["tasks.read"] },
  dev: { users: [{ id: "ada", roles: ["member"] }] },
});
export const tasks = app.collection("tasks", { title: s.string(), done: s.boolean() });
```

```ts
// feltkit/tasks.ts
import { fail, s } from "@feltdb/feltkit";
import { app, tasks } from "./app.js";

export const list = app.query({
  access: "tasks.read",
  capability: { name: "tasks.list" },
  returns: s.array(s.object({ id: s.string(), title: s.string(), done: s.boolean(), __version: s.number() })),
  handler: (ctx) => ctx.db.find(tasks, {}),
});

export const create = app.mutation({
  access: "tasks.write",
  args: { title: s.string() },
  handler: (ctx, { title }) => ctx.db.insert(tasks, { title, done: false }),
});

export const complete = app.mutation({
  access: "tasks.write",
  args: { id: s.string() },
  handler: async (ctx, { id }) => {
    const task = await ctx.db.get(tasks, id);
    if (!task) fail("NOT_FOUND", `No task ${id}`);
    return ctx.db.patch(tasks, id, { done: true });
  },
});
```

`ctx` in a handler: `ctx.db` (reads; writes in mutations, committed atomically when the handler returns),
`ctx.auth` (`principal`, `has(permission)`, `require(permission)`, `requirePrincipal()`), `ctx.services`
(see the feltkit-services skill), `ctx.environment`, `ctx.requestId`, `ctx.log`. `ctx.unsafe.feltdb` bypasses
validation and the transaction: do not use it unless the user asks and understands that.

## Existing APIs and model decisions

Connect an HTTP API the user already runs as AppPort capabilities (never call `fetch` from a mutation):

```ts
export const payments = app.integration("payments", {
  baseUrl: { env: "PAYMENTS_URL", development: "http://127.0.0.1:4010" },
  credential: "credential-ref:payments",            // value in FELTKIT_CREDENTIAL_PAYMENTS, never in code
  operations: {
    create: { method: "POST", path: "/payments", input: { invoiceId: s.string(), amount: s.number() }, output: s.object({ id: s.string() }),
              effect: "consequential", access: "payments.write", idempotencyHeader: "Idempotency-Key",
              verify: { operation: "lookup", input: { invoiceId: { $input: "/invoiceId" } }, expect: [{ at: "/status", equals: "paid" }] } },
    lookup: { method: "GET", path: "/payments/by-invoice/{invoiceId}", output: s.object({ status: s.string() }), effect: "observation", access: "payments.read" },
  },
});
```

A consequential call whose outcome is unknown is never re-sent; declare `verify` so it can be settled from the API.
To let the environment's model choose a next step, start a decision from a mutation with the options you allow:
`ctx.agent.start({ objective, decision: { question, options: [{ id, label, capability?, input? }] } })`.
The choice is a proposal; consequential options wait for a person. See `examples/invoices` in the FeltKit repo.

## Testing

```ts
import { test } from "node:test";
import assert from "node:assert/strict";
import { createTestApp } from "@feltdb/feltkit/testing";
import { api } from "../feltkit/_generated/api";

test("a member completes a task", async () => {
  const app = await createTestApp();
  try {
    const id = await app.as("ada").mutation(api.tasks.create, { title: "x" });
    await app.as("ada").mutation(api.tasks.complete, { id });
    await app.restart(); // same state, new runtime: proves durability
    assert.equal((await app.as("ada").query(api.tasks.list)).length, 1);
  } finally {
    await app.close();
  }
});
```

Each test app gets an isolated FeltDB instance. Test denials too (`app.as("viewer")` should be refused writes).

## When to stop and ask

- Changing roles or `access` (it changes who can do what everywhere, including agents and API keys).
- Renaming the application (`name` selects the FeltDB namespace: a rename starts from empty state).
- Deleting collections or data, or using `ctx.unsafe.feltdb`.

## Compatibility

Written for `@feltdb/feltkit` 0.1.x (Node 20.11+). Commands: `feltkit create`, `dev`, `build`, `start`, `test`,
`inspect`, `deploy`, `session`, `operator`, `readiness`, `model`, `codegen`, `doctor`, `skills`. Verified in Claude Code only.
